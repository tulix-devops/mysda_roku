## Focus checks (the dispatcher's list): what holds

- **One request in flight:** `pump` returns while `m.reqTask` is set (:243), and only `onStateLoaded` clears it. The first call uses `m.task`, a separate slot, but the state pump only starts after it has landed. Holds.
- **Focused state first:** pump serves the focused state, then its next page, then the state below (:246-258). Holds, apart from C5.
- **No lost requests:** a rest-timer fire while a request is in flight returns early, and the landing pumps again (:303). No lost request found.
- **No duplicate requests:** `device-log-5` has 38 request lines, all 200, with no duplicates (`uniq -d` empty).
- **Stale answers:** an answer is applied to the node it was requested for (`m.reqIdx`). State nodes never re-order, and the name is cross-checked (:285). Repainting happens only when that state is focused. A late answer for a state focus has left is cached, not dropped. That differs from the contract's "drop", and it is better.
- **Page-1 seeding:** a state is seeded only when the page holds at least its `states[]` count (:197). Canada, partly on page 1 (4 of 16), is not seeded; this checks out against the live API. If a row is dropped, a state is simply not seeded and costs one extra request, which is harmless. If `states[]` under-counted, the state would be seeded short with `pages = 1`. That cannot happen within one response (probed: all 42 counts match the rows).
- **Past-end quirk:** paging uses the answer's `paging.page` and `paging.pages` (:286). A past-end request returns the real last page number (probed), and dedupe absorbs the repeated rows, so it stops correctly.
- **Task field rename:** `stateName` avoids the Task's own `state` field (ScChurchTask.xml:25). This is the same class as KB `reserved-words-and-name-collisions`, and the console proves it (device-log-1/2 against 4/5).
- **First-call failure and OK retry:** OK is handled only when `stateCount() = 0`, `m.task` is invalid and `m.data` is invalid (:589-595), and `loadFirst` creates a fresh Task (KB `skeleton-replacing-a-modal-loader-four-traps`, trap 4). Re-entering the screen also retries (:156). Read, not device-verified, as the report says.
- **Right into an unloaded state:** nothing happens (:609 needs rows). **Left and Up while loading** in the states column behave as before.
- **Compile and runtime:** the deployed zip matches the source, and the 42-state walk produced no errors in the log. No reserved-word identifiers (`build`, `replace`, `page` and `per` are not reserved).
- **Render-thread cost:** at most 100 node copies per landing, plus a 42-entry `scStates` scan. Negligible.

## Notes

- Data issue, backend: the API truncates city names to their first word ("Bay" for Bay Roberts, "Mount", "San", "Santa"; visible in 03-canada-loaded). The report flags it; this is for the backend owner, not the client.
- The subtitle total (`paging.total` from the first call) and the state counts are not refreshed after the first call, except the fetched state's own count. Fine for a session.
- `isFresh` uses wall-clock seconds (`roDateTime`). If the clock is set back, a state stays "fresh" longer. Negligible.
- I unzipped out/mysdatv.zip into the session scratchpad only, to compare hashes. Nothing in the repo was written apart from this file.
- Learnings candidates for the orchestrator:
  1. "A paging branch must honour the same failed flag as the first-page branch, or a failed next page re-requests itself on every landing." This is a Roku instance of `long-list-and-grid-craft` (every outcome needs its own state).
  2. "A loaded-but-empty answer needs its own visible state, distinct from loading."
  3. "A paged API that honours a small per_page lets you device-test page 2 today (per_page=12)."
